BEAMFOAM INTEGRATION INTO SOLIDS4FOAM: CHANGE SUMMARY
===================================================

Initial migration date: 21 September 2026
For the 21 October 2026 transfer to current upstream development, see
beamFoam-upstream-validation.txt in this directory.
Implementation: first-phase standalone beam solidModel integration
Validated platform: OpenFOAM.com v2412, linux64GccDPInt32Opt, serial execution

Paths below are relative to solids4foam-master unless stated otherwise.

1. Objective and agreed scope
-----------------------------

The objective was to run beamFoam's core static and dynamic beam mechanics
through the existing solids4Foam application as a genuine runtime-selectable
solidModel. The implementation retains the existing beam formulation, beam
mesh workflow, beamProperties dictionary, and W/Theta primary fields.

The initial compilation and validation target is OpenFOAM.com v2412.
v2306, v2312 and v2512 remain desired compatibility targets; they have not
been compiled or tested in this migration.

The validated scope covers standalone beam analysis, core beam boundary
conditions, cross-section configuration, and the mesh/reference-position
utilities. Fluid-beam coupling, parallel and multi-region operation, and
optional spring/contact/wave/Morison loading are outside this phase.

2. Resulting architecture
-------------------------

Runtime construction now follows this path:

    solids4Foam.C
        physicsModel::New(runTime)
            physicsProperties: type solid
                solidModel::New(runTime, region)
                    solidProperties: solidModel beamSolid
                        beamSolid : public solidModel
                            beamModel::New(runTime, region)
                                beamProperties:
                                    coupledTotalLagNewtonRaphsonBeam

beamSolid is registered in the existing solidModel selection table using
TypeName, defineTypeNameAndDebug, and addToRunTimeSelectionTable. It is not a
separate top-level beam physicsModel and does not introduce a new executable.

The implementation uses two libraries:

    libS4FBeamModels.so  Imported beam mechanics and supporting classes
    libS4FBeamSolid.so   New solidModel adapter

Cases load libS4FBeamSolid.so through the controlDict libs entry. Its linked
dependencies bring in the beam implementation and solids4Foam model library.
The existing solids4Foam.C application and its runtime selection factories
were not changed.

3. Imported beam implementation
-------------------------------

The source tree beamFoam-main/src/wireBunchingModels was imported into:

    src/beamModels/

The library retains the beamModel base/factory, the
coupledTotalLagNewtonRaphsonBeam implementation, section models including
circle/rectangle/annularSector, beam boundary conditions, numerical helpers,
Eigen-based block solver, and beam function objects for displacement,
force/moment, energy, and convergence output.

The coupled equation assembly, Newton-Raphson evolution, and numerical
helper implementations were preserved. This is an integration of the existing
beam mechanics, not a replacement with a continuum-solid formulation.

Existing optional contribution classes remain in the imported source/build
list to avoid refactoring the library's dependencies during this phase.
Their presence does not establish validated spring, contact or environmental
loading support through solids4Foam.

Compared with the original source tree, the changed imported files are:

    Allwmake
    Make/files
    beamModels/beamModel/beamModel.H
    beamModels/beamModel/beamModel.C
    beamModels/coupledTotalLagNewtonRaphsonBeam/
        coupledTotalLagNewtonRaphsonBeam.H
        coupledTotalLagNewtonRaphsonBeam.C
    The renamed fixedDisplacement boundary-condition .H/.C pair
    The renamed fixedRotation boundary-condition .H/.C pair

The original beamFoam-main source tree was retained for reference.

4. Beam mesh and C++ ownership
-----------------------------

The beam mesh remains the mesh generated by createBeamMesh. The migration
does not replace it with a blockMesh-generated continuum mesh or change its
points, faces, beam cell zones, connectivity, or section configuration.

The solidModel constructor loads the generated beam mesh for the selected
region. Previously, constructing the embedded beamModel would independently
construct another dynamicFvMesh for the same region. The imported beamModel
now separates ownership from access:

    meshOwnerPtr_: owns a mesh only when the beam model creates one
    meshPtr_:     references the mesh used by the beam model

If the region already has a registered dynamicFvMesh, beamModel borrows it.
Otherwise, it constructs and owns a mesh using its existing creation path.
The mesh() accessor dereferences the selected mesh pointer. The borrowed mesh
is not deleted by the embedded beam model.

A second change addresses the pointMesh wrapper. The beam implementation
previously held its own pointMesh value object. The inherited solidModel
point fields use pointMesh::New(mesh). OpenFOAM rejected assignment between
pointW and pointD because the two fields referenced different pointMesh
objects, even though the underlying beam geometry was the same.

The imported coupled beam model now stores:

    const pointMesh& pMesh_;

and initializes it using pointMesh::New(mesh()). Both sets of point fields
therefore reference the registered wrapper around the same beam mesh.

These changes concern C++ object ownership and identity. They do not alter
beam geometry, discretisation, or the displacement/rotation reconstruction.

5. New beamSolid adapter
------------------------

New implementation and build files:

    src/beamSolid/beamSolid.H
    src/beamSolid/beamSolid.C
    src/beamSolid/Make/files
    src/beamSolid/Make/options
    src/beamSolid/Allwmake

The adapter owns an autoPtr<beamModel> and provides the required solidModel
interface while delegating the actual solve to the beam implementation.

Its behavior is as follows:

  - nonLinGeom() reports TOTAL_LAGRANGIAN.
  - solutionD() returns the existing W beam displacement field.
  - U() returns the beam's registered translational velocity field.
  - evolve() invokes the beam evolution and returns true on normal completion.
    The beam solver returns an initial residual, which is not cast to bool.
    Its existing convergence failures remain fatal errors.
  - updateTotalFields() runs the beam update and synchronizes the inherited
    displacement interface fields.
  - writeFields() delegates to the beam writer and avoids the continuum
    solidModel stress/strain post-processing path.
  - tractionBoundarySnGrad() reports an error for continuum traction boundary
    conditions. Beam force/moment boundary conditions must be used instead.

The interface field mapping is:

    D       <- W
    DD      <- D - D.oldTime()
    pointD  <- pointW
    pointDD <- pointD - pointD.oldTime()

pointW retains the original reconstruction, including cross-section rotation.
The constructor initializes these fields and their initial old-time values.
The inherited D, DD, pointD, pointDD and sigma fields are marked NO_WRITE in
the adapter, so unused continuum fields are not presented as beam results.
The inherited solidModel still allocates its usual interface storage.

W and Theta remain the primary beam unknowns. The existing section force,
moment, strain, point displacement and history outputs remain available.
The beam update overrides also avoid invoking the continuum mechanical-model
update for the beam solve; a mechanicalProperties dictionary is not required
by the supplied beam cases.

No adaptive-time-step behavior was added. The original beamFoam application's
separate time-control headers were not active in its main loop, so their
presence was not treated as functionality that needed enabling during migration.

6. Boundary-condition name conflicts
------------------------------------

Both original libraries defined fixedDisplacement and fixedRotation with
identical C++ class names and runtime selection names. Loading those original
implementations together would introduce symbol and registration conflicts.

Only the imported beam versions were renamed:

    fixedDisplacement -> beamFixedDisplacement
    fixedRotation     -> beamFixedRotation

The changes include class names, constructors, header guards, filenames,
source directories, runtime TypeName strings, and Make/files entries.
The migrated tutorial dictionaries use the new names.

The existing solids4Foam continuum boundary conditions retain their original
names and implementations. Other beam boundary-condition names are unchanged.
Do not explicitly load the original libwireBunchingModels alongside the migrated
beam libraries: other imported beam classes still share their original names.

7. Utilities and build integration
----------------------------------

Imported utility directories:

    applications/utilities/createBeamMesh/
    applications/utilities/setInitialPositionBeam/

createBeamMesh now includes src/beamModels headers and links libS4FBeamModels.
The obsolete createCircularBeamMesh include path was removed from its build
options. Its mesh-generation implementation was retained.

setInitialPositionBeam retains its original implementation and OpenFOAM
library dependencies. It provides the existing translation/rotation reference
configuration setup used by the dynamic tutorial.

Both utilities keep their existing executable names. With the current user
build configuration they install into the same FOAM_USER_APPBIN as the
original utilities; they are not installed under separately suffixed names.

Existing build files modified:

    src/Allwmake
        Builds beamModels and then beamSolid after solids4FoamModels for
        OpenFOAM.com versions when S4F_NO_USE_EIGEN is empty/unset.

    src/Allwclean
        Adds cleaning of beamSolid and beamModels build targets.

New utility Allwmake scripts apply the same OpenFOAM.com/Eigen gating when
called through the application build traversal. OpenFOAM.org and foam-extend
build workflows skip these new targets; they have not been ported here.

The imported library output was renamed from libwireBunchingModels to
libS4FBeamModels. The adapter builds libS4FBeamSolid and includes solids4Foam's
compatibility flags and existing ThirdParty/eigen3 headers.

Allwmake argument handling was corrected to use WM_PROJECT_DIR and the parsed
targetType, avoiding forwarding the parser's -fromWmake option to wmake.
The normal root build discovers the additions through the existing src and
applications traversal. The top-level application source remains unchanged.

8. Case configuration and tutorials
-----------------------------------

Three clean tutorials were added under tutorials/solids/beamsPlatesShells:

    beamCantilever         Based on beamFoam tutorials/cantilever
    beamDynamicCantilever  Based on tutorials/3dDynamicCantilever
    beamFollowerForce      Based on tutorials/cantileverFollowerForce

Each tutorial contains initial fields, constant/system dictionaries, Allrun,
Allclean and a short README. Generated meshes, old time directories and old
postProcessing results were excluded. startFrom is set to startTime to ensure
fresh validation from zero. The controlDict compression spelling was updated
from uncompressed to off for v2412.

The case additions are:

    system/controlDict:
        application solids4Foam;
        libs ("libS4FBeamSolid.so");
        startFrom startTime;
        startTime 0;

    constant/physicsProperties:
        type solid;

    constant/solidProperties:
        solidModel beamSolid;
        beamSolidCoeffs
        {
            solutionAlgorithm implicitCoupled;
            infoFrequency 1;
        }

Retain the original beamProperties and W/Theta fields, with the two renamed
beam boundary types. Material/section data and beam solver tolerances remain
in beamProperties. The adapter does not replace the beam numerical algorithm
with a continuum solver selected by the inherited solutionAlgorithm setting.

A constant/g uniformDimensionedVectorField is supplied as required by the
solidModel base. Cases without gravity use dimensions [0 1 -2 0 0 0 0] and
value (0 0 0).

Allrun calls createBeamMesh and solids4Foam. The dynamic tutorial additionally
calls setInitialPositionBeam for beam_0 with the original 90-degree rotation
about (0 -1 0). Plotting and GUI-opening commands are not required by the new
Allrun scripts. Allclean uses the standard OpenFOAM cleanCase helper.

9. Compilation and validation performed
---------------------------------------

Compilation was performed incrementally after the library import, boundary
renames, mesh ownership change, pointMesh ownership change, adapter creation
and compiler fixes, utility import, and build-script integration. The final
adapter and all new build entry points completed successfully on v2412.
The unchanged solids4Foam executable target was also checked with wmake.
This is not a claim of a full clean rebuild on all OpenFOAM variants.

The first adapter compilation exposed a missing Eigen include path; it was
added and the target rebuilt. The first runtime construction exposed the
pointMesh identity mismatch; sharing pointMesh::New resolved it. Build-entry
point testing caught the -fromWmake forwarding issue described above.

The supplied original static cantilever folder contained prior results.
An early latestTime run therefore skipped time advancement. Those early
results were not accepted as the numerical validation. Final comparisons used
clean input-only directories and fresh runs from zero. The dynamic comparison
included the tutorial's reference-rotation utility step.

Final comparison results:

    Original case              Field files checked   Differences
    cantilever                 900                   0
    3dDynamicCantilever         900                   0
    cantileverFollowerForce    900                   0
    TOTAL                      2700                  0

Each reference field file was compared with the migrated counterpart at every
written output time. Text comparisons normalized only the two renamed beam
boundary types. This is exact equality at the cases' configured output
precision, not a claim of bitwise equality of unprinted in-memory values.

The 11 postProcessing history files also matched byte-for-byte:

    cantilever:              3 displacement/convergence/force-moment files
    3dDynamicCantilever:      5 files including energy histories
    cantileverFollowerForce: 3 displacement/convergence/force-moment files

The cantilever mesh utility check found seven byte-identical mesh files:

    boundary, cellZones, faces, neighbour, owner, pointZones, points

The existing solids4Foam linearElasticity/patchTest case also ran successfully
with libS4FBeamSolid explicitly loaded. This exercises the continuum model and
its original fixedDisplacement boundary condition with the beam libraries
present. It is a focused coexistence regression, not the full toolbox suite.

10. Restart finding and remaining limits
----------------------------------------

The rotated dynamic case was restarted from the saved time 0.5 and run to 1
using both the original and migrated solvers. Both completed, and their final
W files were identical. However, the restarted W differed from the final W
of the uninterrupted run.

This reproduces an existing beamFoam restart limitation. The original model
marks dynamic state fields such as U, Accl, Omega and dotOmega NO_WRITE.
The migration preserves that policy and has not implemented or validated
complete restart-state persistence. The inherited solidModel restart switch
does not by itself provide that missing beam state.

Use uninterrupted time-zero runs for the validated dynamic workflow. A restart
improvement needs a separate state-persistence audit, followed by split-run
versus continuous-run validation of displacement, rotation, velocity, energy,
and any required rotation/history variables. Merely completing a restarted
run is not an acceptance criterion for correct dynamic restart.

Other limits are:

  - Only v2412 was compiled and tested; v2306/v2312/v2512 remain unverified.
  - Only serial, single-region standalone beam cases were validated.
  - Fluid-beam interface mapping and load transfer have not been implemented.
  - Optional spring/contact/wave/Morison behaviors were not validated.
  - Populating displacement interfaces does not establish compatibility with
    every continuum-solid postprocessor, stress operation, or coupling method.

11. Build, run, and evidence locations
--------------------------------------

For a focused build, from the solids4foam-master root with OpenFOAM sourced
and the existing solids4foam libraries/Eigen dependency already built:

    src/beamModels/Allwmake

12. Suggested next work
-----------------------

The next technical priorities are complete dynamic restart support and builds
on the additional requested OpenFOAM.com versions. Parallel/multi-region
validation and optional loading can then be added as separate increments.
Fluid-beam coupling needs its own design for surface kinematics and transfer
of distributed forces and moments; it should not be inferred from the presence
of the solidModel adapter alone.
